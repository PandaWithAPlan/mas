# Диагностика конфигурации development-team

Дата: 2026-07-27 · Версия системы на момент проверки: **1.8.0** (`VERSION`)
Предыдущий диагностический прогон: 1.8.0 (дефекты R1–R7), см. `CHANGELOG.md`.

Цель проверки — найти расхождения между **описанным процессом** и **конфигурацией,
которая его обеспечивает**, а также проверить утверждения конфигурации о движке
opencode по его фактическому поведению.

---

## 0. Резюме

Формальная целостность конфигурации в порядке: все три линтера зелёные, CI покрывает
JSON-валидность, карту навыков, права на запись и провенанс памяти (с позитивной и
негативной фикстурой). Дефектов класса R1–R7 («агенту предписано записать файл, а
движок запретит») внутри глобального слоя не осталось.

Основные проблемы лежат в двух других плоскостях:

1. **Модель прав опирается на семантику glob, которой у opencode нет.** Деналист
   секретов написан в синтаксисе `**/...`, а движок globstar не поддерживает —
   `*` разворачивается в `.*`, `**` отдельной конструкцией не является. Корневой
   `.env` может остаться незакрытым. Это главный предохранитель всей конфигурации.
2. **Проектный слой (`project-config/`) отстал от глобального на релиз.** Шаблон,
   который копируется в каждый новый проект, описывает схему памяти до WI-1…WI-6
   и назначает владельцем документации `coder-back`/`reviewer` вместо `doc-keeper`.
   Это тот же класс дефекта, что R4 (отставание CHECKLIST), но в файле с большим
   радиусом поражения.

Ниже — находки по убыванию серьёзности. К каждой указано, чем подтверждена.

## 1. Критические — проверить до следующего развёртывания

### C1. Деналист секретов, вероятно, не закрывает корневой `.env`

`global-config/opencode.json`:

```json
"read": {
  "*": "allow",
  "**/.env": "deny",
  "**/.env.*": "deny",
  "**/*.key": "deny",
  "**/*.pem": "deny",
  "**/id_rsa*": "deny",
  "**/*.secret": "deny",
  "**/secrets/**": "deny",
  "**/.aws/**": "deny",
  "**/.ssh/**": "deny"
}
```

Фактическое поведение движка (issue [sst/opencode#22465](https://github.com/anomalyco/opencode/issues/22465),
закрыт как *not planned*): *«a single `*` is replaced with `.*` in regex»*, **globstar
не поддерживается**, и *«different permission keywords use inconsistent path matching
(absolute vs. relative paths)»*.

Следствие: `**/.env` компилируется примерно в `.*.*/\.env` — шаблон **требует
литерального `/` перед именем файла**. Для относительного пути `.env` (корень
проекта — самое типичное расположение) совпадения не будет. То же для
`**/secrets/**`, `**/.aws/**`, `**/.ssh/**` в корне.

Показательно, что собственный пример в документации opencode использует
`"*.env": "deny"`, а не `"**/.env"`.

Риск: агенты (`explorer`, `analyst`, кодеры, `guardian`) получают в контекст сырые
секреты, при том что README объявляет это закрытым и называет `devops` «единственным
местом, где сырые секреты попадают в контекст модели».

Порядок правил при этом **корректен**: catch-all `"*"` стоит первым, побеждает
последнее совпавшее правило — это соответствует документации движка.

**Действие:** продублировать каждый шаблон без префикса `**/` (`.env`, `.env.*`,
`*.env`, `*.key`, `*.pem`, `id_rsa*`, `*.secret`, `secrets/**`, `.aws/**`, `.ssh/**`).
Избыточность здесь бесплатна. Затем — эмпирическая проверка на целевой версии:
попросить `explorer` прочитать `./.env` и зафиксировать фактический результат.

### C2. `"*": "deny"` у кодеров — проверить, что инструмент не отключается целиком

Вся схема адаптации построена на том, что глобально кодеры имеют
`edit: {"*": "deny"}` (fail-fast по замыслу, `AGENTS.md`, Critical Gotchas), а
проектный `opencode.json` открывает конкретные зоны.

Issue [sst/opencode#7029](https://github.com/anomalyco/opencode/issues/7029)
(bug, открыт 2026-01-06, **закрыт**): *«if you set `"*": deny` the whole tool no longer
works. Specific patterns should take precedence over wildcard denys»*.

Баг закрыт, то есть, скорее всего, исправлен. Но если на используемой версии он
воспроизводится, кодеры не смогут писать **никуда** независимо от проектных allow —
основной сценарий системы не заработает, и симптом будет выглядеть как «модель
отказывается редактировать», а не как ошибка конфигурации.

**Действие:** одноразовый тест на целевой версии до развёртывания. Результат
зафиксировать в README, раздел «Проверка после установки».

### C3. Провайдер `ollama-cloud` в конфиге не определён

Все 12 агентов используют модели вида `ollama-cloud/<model>`, но блока `provider`
в `global-config/opencode.json` нет. Канонический id для Ollama в opencode — `ollama`,
задаётся пользовательским блоком `provider` с `npm: "@ai-sdk/openai-compatible"` и
`baseURL`. Полный id модели — `provider_id/model_id`, где `provider_id` — ключ из
секции `provider` конфига.

README честно называет модели примерами и требует настроить провайдера, но
**готового блока `provider` нигде нет**, а CHECKLIST (документ, по которому
разворачивают систему) вообще не содержит шага «настроить провайдера и проверить,
что модели резолвятся».

Отдельно: `devops` стоит на обязательном префлайт-гейте перед кодерами —
нерезолвящаяся модель там останавливает конвейер, что README уже отмечает.

**Действие:** либо добавить пример блока `provider` в `global-config/opencode.json`
(закомментированный нельзя — файл строгий JSON, значит в README), либо вынести это
отдельным шагом CHECKLIST с чекбоксом `/models`.

### M2. Шаблон назначает владельцем документации не того агента

```
├── [ДОКУМЕНТАЦИЯ]/                     ← [владелец: coder-back / reviewer]

Строка 21 — конвейер без Doc Keeper:

```
Explorer → Analyst → Architect → [DevOps: префлайт] → Coder(s) → Tester → Guardian → [Team Lead: решение] → Reviewer

### M4. В `development-team/README.md` дважды описана автоматическая адаптация

Раздел «Автоматическая адаптация через `ai-engineer`» присутствует **два раза** —
строки 205–238 (как рекомендуемый путь, до ручной адаптации) и строки 290–335
(как подраздел внутри ручной адаптации), **с двумя разными текстами промпта**
(6 пунктов против 3 + блок ОГРАНИЧЕНИЯ) и двумя разными командами запуска
(`opencode run --agent ai-engineer` против `opencode --agent ai-engineer`).
В оглавлении раздел один. Читатель не может понять, какой промпт актуален.

### M5. Конвенция именования артефактов нарушена, а линтер под это подстроен

`project-config/AGENTS.md` (строки 182–186) требует **строго 3-значный** номер
цикла и явно запрещает отклонения. При этом `html-report/SKILL.md` инструктирует
писать `work-area/reports/final-report-N.html` (строки 338, 348, 366) — одиночный `N`.

В `check-artifact-permissions.sh` есть специальный случай под это расхождение:

```python
p = re.sub(r"-N(\.[A-Za-z]+)$", r"-1\1", p)   # final-report-N.html и подобные
```

То есть линтер научили принимать нарушение конвенции вместо того, чтобы его
устранить. Практический эффект: `final-report-1.html` и `final-report-001.html`
для `reviewer` неразличимы (право `final-report-*.html` покрывает оба), но
`report-data-extract` и `session-init` ищут артефакты по `NNN`.

### M6. Версия CHECKLIST снова отстаёт

`CHECKLIST.md`, строка 3: «Версия чеклиста: **1.7.0**» при `VERSION` = **1.8.0**.
Содержательно чеклист обновлён в 1.8.0 (шаги 4.1–4.4 соответствуют текущей схеме
памяти), но заголовок не бампнут — тот же дефект R4 в лёгкой форме, и он ничем
не проверяется.

### M7. Карта навыков продублирована в трёх местах и уже разошлась

Источник истины — `global-config/skills/README.md`. Его копии:
`global-config/AGENTS.md` (таблица прав и Quick Reference) и
`project-config/AGENTS.md` (три таблицы навыков, строки 98–131).

`check-skill-map.sh` сверяет только «каталог навыка ↔ строка в `skills/README.md`».
Копия в `project-config/AGENTS.md` не проверяется ничем и **уже разошлась**: в
списке потребителей `memory-retrieve` (строка 100) перечислены 10 агентов без
`doc-keeper`, хотя глобальное правило — «Every agent calls `memory-retrieve` as
their first action», и `doc-keeper.md` его вызывает.

## 3. Средние — гигиена, наблюдаемость, документирование модели угроз

### D1. Bash-деналист — блэклист по началу командной строки

Матчинг идёт по полной командной строке шаблоном с `*` → `.*`. Шаблон `curl*`
совпадает только с командой, **начинающейся** с `curl`. Не покрыты:

- цепочки и подстановки: `cd /tmp && curl …`, `sh -c 'curl …'`, `xargs curl`, `$(which curl)`;
- альтернативные каналы эксфильтрации: `scp`, `rsync`, `ftp`, `sftp`, `telnet`,
  `openssl s_client`, `python3 -c "import urllib…"`, `node -e`, `/dev/tcp`;
- альтернативные способы разрушения: `rm -fr`, `rm -r -f`, `find … -delete`,
  `git clean -fdx`, `truncate`, `dd`, `> файл`.

Это нормальное свойство блэклиста, и `guardian` + `external_directory: deny`
служат бэкстопом. Но README в «Известных ограничениях» описывает только обход
`edit` через шелл и **не описывает обходимость самого деналиста** — заявка
«закрывая каналы порчи и эксфильтрации» (README, строка 121) сильнее, чем
конфигурация реально обеспечивает. Наиболее значимо для `devops`: у него есть
read-override на `.env`.

### D2. Read-override у `devops` можно перестать считать неопределённостью

README (строка 351) держит коллизию «глобальный `deny` на `.env` против
агентского `allow` у `devops`» как неразрешённую: «оба исхода правдоподобны».
По документации движка агентские права мержатся с глобальными и **имеют
приоритет**, а внутри карты побеждает последнее совпавшее правило. То есть
override срабатывает и сырые секреты попадают в контекст `devops`.

Формулировку можно свести к однозначной, а дефолт — пересмотреть: если задача
`devops` сводится к генерации `.env` из `.env.example`, блок `read` не нужен.

### D3. Линтер моделирует glob не так, как движок

`check-artifact-permissions.sh`, строки 63–80:

```python
def glob_to_re(pattern):
    """opencode-подобная семантика: ** пересекает /, * — нет."""
```

Фактическая семантика движка обратная: `*` → `.*` (пересекает `/`), globstar
как отдельной конструкции нет. Комментарий фактически неверен, а модель линтера
**строже** движка. Проверки на текущем наборе шаблонов проходят одинаково в обеих
моделях, поэтому ложных срабатываний сейчас нет — но линтер даёт неверную картину
широты прав: `guardian-*.md` в движке покрывает и `guardian-x/y.md`, а
`"*": "deny"` действительно закрывает всё (в модели линтера — только корень).

### D4. Пробелы в CI

`.github/workflows/config-checks.yml` не проверяет:

- `project-config/opencode.json` — вообще никак, даже как JSONC (JSONC движком
  поддерживается, предупреждение в CHECKLIST корректно, но синтаксическая
  поломка шаблона пройдёт в main незамеченной);
- согласованность `VERSION` ↔ `CHECKLIST.md` ↔ верхняя запись `CHANGELOG.md` (M6);
- резолвится ли каждый `skill({ name: "X" })` из файлов агентов в существующий
  каталог навыка (сейчас — да, проверено вручную, но инварианта нет);
- копию карты навыков в `project-config/AGENTS.md` (M7).

### D5. Мусорный workflow `push-claude-branch.yml`

`.github/workflows/push-claude-branch.yml` — одноразовая автоматизация с
`permissions: contents: write`, которая по `workflow_dispatch` перезаписывает
`development-team/project-config/opencode.json` захардкоженным содержимым.
Это содержимое **устарело**: в нём нет блоков LSP для C/C++, которые есть в
текущем файле, и нет комментариев-инструкций. Коммит-сообщение содержит ссылку
на чужую сессию и упоминание внутреннего названия проекта. Запуск workflow
откатит шаблон на старую версию. Удалить.

### D6. Разнобой во front-matter навыков

18 из 22 навыков используют плотный блок:

```yaml
---
name: …
---
```

Четыре — `doc-consistency-check`, `doc-scan-rules`, `doc-update-arch`,
`doc-update-module` — содержат пустые строки сразу после открывающего `---` и
перед закрывающим. YAML это переживает, но парсеры front-matter, требующие
непосредственного начала документа, могут не распознать блок — а именно у
`doc-update-arch` и `doc-update-module` во front-matter лежит поле `writes:`,
на котором держится линтер прав. Нормализовать.

### D7. `memory-summarize` в карте навыков помечен неточно

Навык не вызывается ни из одного файла агента — только транзитивно из
`memory-update` (проверено grep'ом по `global-config/agents/`). В карте он
значится как вызываемый `team-lead` без пометки о транзитивности, тогда как
для аналогичного `psao-annotate` пометка есть и явно указана точка вызова.
После R7 (где именно завышенный охват `psao-annotate` был дефектом) стоит
привести к одному виду.

### D8. Плейсхолдеры в разделе, помеченном «не требует адаптации»

`project-config/AGENTS.md`, строка 197: «Этот раздел не требует адаптации», при
этом строки 199–200 содержат `[DOCS_DIR]/` и `[TESTS_DIR]/`. CHECKLIST (Шаг 5)
требует, чтобы плейсхолдеров не осталось. CI-проверка на плейсхолдеры сканирует
только `global-config/`, поэтому противоречие не ловится.

### D9. Разрыв в инструкциях по развёртыванию

CHECKLIST начинается сразу с копирования `project-config/`; шага «развернуть
глобальный слой в `~/.config/opencode/`» в нём нет вообще — он только в README.
При этом Шаг 4.4 CHECKLIST уже ссылается на
`~/.config/opencode/skills/check-memory-provenance.sh`, а Шаг 5 — на
`global-config/skills/…`. Человек, работающий строго по чеклисту, до первой
ссылки на `~/.config/opencode/` ничего туда не клал.

### D10. Легаси в переносимом шаблоне

`project-config/AGENTS.md` (строки 144, 213) и `team-lead.md` (строка ~155)
описывают `work-area/memory/MEMORY.md` как «замороженный». Это артефакт
исходного проекта, с которого шаблон снимали: в новом проекте такого файла
никогда не было, и правило «он заморожен» только запутывает.

## 5. Рекомендации — предлагаемый порядок работ

**Этап 1 — «конфигурация делает то, что заявляет» (C1–C3).**
Требует одноразовой эмпирической проверки на целевой версии opencode. До неё
любые утверждения README о модели безопасности остаются гипотезой. Правка
деналиста секретов — несколько строк JSON и обновление README/CHECKLIST.
Наибольшая отдача на единицу работы.

**Этап 2 — синхронизация проектного слоя (M1, M2, M7, D8, D10).**
`project-config/AGENTS.md` — единственный файл, попадающий в каждый новый проект,
и сейчас он даёт неверную схему памяти и неверного владельца документации.
Правится в один проход, без изменения логики.

**Этап 3 — документация верхнего уровня (M3, M4, M6).**
Корневой README, дедупликация раздела адаптации, бамп версии чеклиста. Механическая
работа, но M4 (два разных промпта на одну задачу) активно вредит новым пользователям.

**Этап 4 — инварианты в CI (M5, D3, D4, D6, D7).**
Каждая находка этой диагностики, которую можно превратить в машинную проверку,
должна ею стать — иначе следующий релиз воспроизведёт тот же класс расхождений.
Минимум: JSONC-валидация проектного шаблона, сверка версий, резолв ссылок на
навыки, единый формат front-matter. Плюс привести `glob_to_re` в линтере к
фактической семантике движка и убрать спецкейс `-N` вместе с исправлением
именования.

**Этап 5 — модель угроз (D1, D2, D5).**
Дописать в «Известные ограничения» обходимость bash-деналиста, свести формулировку
про `devops` и `.env` к однозначной, удалить `push-claude-branch.yml`.

**Оценка:** этап 1 требует доступа к рабочей установке opencode и без него
не закрывается. Этапы 2–5 — правки в этом репозитории, без внешних зависимостей.

## Приложение — источники по поведению движка

- [sst/opencode#22465](https://github.com/anomalyco/opencode/issues/22465) — closed as not planned:
  `*` разворачивается в `.*` (пересекает `/` и `../`), globstar не поддерживается,
  разные permission-ключи используют то абсолютные, то относительные пути.
- [sst/opencode#7029](https://github.com/anomalyco/opencode/issues/7029) — bug, closed:
  `"*": "deny"` отключал инструмент целиком, специфичные allow не имели приоритета.
- [Permissions | opencode](https://opencode.ai/docs/permissions/) — побеждает последнее
  совпавшее правило; агентские права мержатся с глобальными и имеют приоритет;
  bash-шаблоны матчатся по полной командной строке.
- [Config | opencode](https://opencode.ai/docs/config/) — JSONC поддерживается.
- [Providers | opencode](https://opencode.ai/docs/providers/) — id провайдера — ключ
  из секции `provider` конфига; для Ollama канонический id `ollama`.
